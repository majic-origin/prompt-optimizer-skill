# 对照实例

四组完整对照，演示分流判断、A/B/C 缺口处理与重构产物。

## 一、走快速档

用户原话：

```text
帮我把这段 JSON 转成 YAML
```

判断：需求自足，歧义不影响结果。归快速档。

动作：一句话点明约束，直接执行。

```text
按标准 YAML 缩进转换，键顺序保持原样。
```

不输出六模块块。这里输出重构块属于浪费，用户要的是转换结果。

## 二、完整档，先闭合 A 类缺口

用户原话：

```text
帮我写个关于 AI 的公众号文章
```

缺口扫描结果：

| 维度 | 归类 | 内容 |
|---|---|---|
| 目标 | B 可推断 | 写一篇公众号文章 |
| 背景 | A 可澄清 | 面向什么读者，有没有素材 |
| 约束 | A 可澄清 | 篇幅，观点倾向 |
| 交付形态 | B 可推断 | 按成稿处理 |
| 受众 | A 可澄清 | 同行还是外行 |
| 成功标准 | B 可推断 | 按公众号常规标准 |

一轮提问，三个问题带选项：

```text
先确认三件事，各回一个词就行：

1. 读者是谁？同行（有技术背景）还是外行（不懂 AI）
2. 篇幅按多少算？短帖 800 字，标准文 2000 字
3. 观点倾向？解释现象，还是给操作建议

素材方面：你手上有数据或案例吗，没有的话我就只做观点框架，不编数字。
```

用户回答"外行 / 2000 字 / 给操作建议"后，产出重构块：

```markdown
## 目标
写一篇 2000 字的公众号文章，向没有技术背景的读者解释 AI 能做什么，并给出三条可立刻上手的用法。

## 背景
- 读者：非技术从业者，日常工作会接触 AI 工具但不了解原理
- 材料：无现成数据与案例，全部论述基于通用认知与用户可自行验证的操作
- 渠道：公众号，手机端阅读为主

## 关键约束
- 篇幅 2000 字，浮动不超过 10%
- 段落短，单段不超过四行，适配手机屏
- 不出现未经核实的数字、机构名、产品数据
- 禁止：把推测写成结论；禁止使用"有研究表明"这类无主体来源

## 执行步骤
1. 开篇给出一个读者日常能遇到的场景
2. 用一段说明 AI 的边界，收住预期
3. 给三条具体用法，每条写清操作步骤与预期效果
4. 结尾回到读者的下一步动作

## 输出格式
Markdown。一级标题一个，二级标题三到四个，正文分段。三条用法各自独立成节。

## 验收标准
- 无技术术语，或术语出现时当句解释
- 每个数字都能指出来源，指不出来的已删除
- 单段不超过四行
- 字数落在 1800 到 2200 之间
- 三条用法都能被读者当天执行
```

关键取舍：素材缺口没有靠编数字填上，而是写进背景模块，让执行阶段不去编。这是缺口处理与防幻觉约束的接口位置。

## 三、完整档，用户已经说清楚了

用户原话：

```text
我们要给客服团队做一个知识库检索工具，用 Python，后端 FastAPI，前端先不管，
数据是现有的 3000 条 FAQ，存在 MySQL 里。需要支持语义检索，不用关键词匹配。
先给我技术方案，别写代码。
```

缺口扫描结果：六个维度里五个 B 可推断，成功标准 B 可推断。没有 A 类缺口，跳过提问。

```markdown
## 目标
为客服团队的 3000 条 FAQ 设计一套语义检索的技术方案，产出方案文档，不含代码。

## 背景
- 技术栈：Python，后端 FastAPI
- 数据：现有 3000 条 FAQ，存于 MySQL
- 使用者：客服团队，通过后端接口调用
- 前端形态本次不涉及

## 关键约束
- 检索方式为语义检索，不用关键词匹配
- 本阶段只出方案，不写实现代码
- 方案要基于现有数据规模，不假设未来数据量
- 禁止：推荐无法在现有环境落地的组件；禁止给出未经验证的性能数字

## 执行步骤
1. 说明在 3000 条规模下语义检索的可行实现路径，给出两到三个选项
2. 逐个说明各选项的数据流，从 FAQ 入库到返回结果
3. 对比各选项的部署成本、维护成本、效果上限
4. 给出推荐项，并说明推荐理由与放弃其他选项的原因
5. 列出方案落地前需要确认的前提条件

## 输出格式
方案文档。先给推荐结论，再给对比。每个选项写成独立小节，含数据流、成本、风险三段。对比部分用表格。

## 验收标准
- 推荐项能在现有 Python 与 FastAPI 环境下落地
- 每个性能相关表述都标明是估算还是实测
- 明确回答 3000 条规模是否需要向量数据库
- 未确认的前提条件单独列出
- 方案中不出现实现代码
```

关键取舍：用户说了"别写代码"，这条原话在约束模块里保住了，防止执行阶段顺手写实现。原话里的硬边界要显式搬进重构块，不能只靠记忆。

## 四、C 类缺口，交付模板

用户原话：

```text
给我写个能吸引人的小红书笔记，关于我家猫的，我想涨粉。
```

缺口扫描结果：

| 维度 | 归类 | 内容 |
|---|---|---|
| 目标 | B 可推断 | 写一篇小红书笔记 |
| 账号定位 | A 可澄清 | 纯宠物号还是生活号 |
| 猫的记忆点类型 | A 可澄清 | 靠外形、行为、还是故事 |
| 猫的实际特征 | C 素材型 | 长相、体型、固定表情，只存在于用户手上 |
| 照片 | C 素材型 | 图像素材，追问拿不到 |
| 真实事件 | C 素材型 | 具体场景与旁人的反应 |

提问两轮，只问 A 类，然后停：

```text
三个问题定方向，猫的具体特征你补一句就行，我不编：

1. 号做什么方向？纯宠物号 / 生活号带猫 / 还没想好
2. 你家猫靠什么让人记住？外形 / 行为 / 故事 / 人猫互动
3. 手上有哪些素材？有照片 / 只有文字 / 有草稿
```

用户答"生活号 / 外形有强特征 / 没图先要文字"后，C 类位置一律挂占位符，产出声明为模板：

```markdown
本稿为模板，补 {{猫的外形特征}} 即可使用。

## 目标
为生活类账号写一篇以猫为主角的小红书笔记，用猫的外形反差制造记忆点，产出标题与正文，带动账号初次涨粉。

## 背景
- 账号定位：生活号，猫是其中一条主线，不做纯宠物号
- 主角：{{猫的外形强特征，一句话}}
- 人设关系：{{你和猫的关系定位}}
- 素材条件：当前无照片，产出纯文字方案，附配图清单
- 平台特性：小红书图文笔记，封面决定点击，标题决定打开

## 关键约束
- 正文 200 到 400 字，短句分段，适配手机屏
- 标题不超过 20 字，把最有反差的点放在前半句
- 标签 5 到 10 个，混合大词与小众词
- 不编造猫的具体信息，未提供的写成占位符
- 不使用无法核实的数字，不承诺涨粉量
- 禁止：把"吸引人"当成已完成的任务；禁止给出无差别的套话文案

## 执行步骤
1. 列出 5 个标题方案，覆盖反差、调侃、共鸣、人设四种钩子
2. 选最强的一个写正文，首句在 15 字内制造停留
3. 给出标签组合
4. 给出配图清单，标出哪张做封面
5. 给出变量表，说明每篇笔记换哪些字段

## 输出格式
标题清单、正文骨架、标签组合、配图清单、变量表。占位符用 {{}} 标出。

## 验收标准
- 每个标题都能在 20 字内说清一个具体反差
- 正文首句能独立成立，不依赖上一句
- 所有待填位置用占位符标出，没有替我脑补的猫的细节
- 标签数量落在 5 到 10 个
- 配图清单明确指出封面用哪一张
- 承诺范围内不含无法核实的涨粉数据
```

密度示例如下，非真实内容，写清示例与真实素材的边界：

```text
它每天早上蹲在门口等饭。
{{特征}}那张脸，配上这个姿势，看着像催债的。
第一次来我家的朋友站在门口不敢进，问我它是不是不高兴。
我说它高兴的时候也这样。
```

变量表：

| 字段 | 每篇替换为 |
|---|---|
| `{{猫的外形特征}}` | 换一个侧面，别每篇都用同一个 |
| 场景 | 吃饭、睡觉、拆家、出门 |
| 旁观者 | 朋友、外卖员、家人 |
| 互动问句 | 一个具体的二选一问题 |

关键取舍：这一轮我拿不到猫的外形与照片，属于 C 类，追问到底也拿不到。所以交付物是模板加变量表，不包装成成稿。上一轮我在同类需求里编了猫的具体特征，那是把 C 类当 B 类填了默认值，是本 skill 要防的错误。

## 四组对照的共同点

快速档与完整档的分界看歧义是否会导致结果偏错，不看请求长短。第一组请求很短归快速档，第三组请求很长归完整档。

缺口的三条出路：A 类问清，B 类填默认并标注，C 类挂占位符并给替换说明。含糊过去不在其中。

用户原话里的硬边界原样搬进约束模块。"别写代码""别编数字""只要方案"，这类否定式要求在重构时最容易丢。

C 类落在核心输入上时，交付物降级为可复用模板。声明是模板、示例与真实素材分开、给出变量表，三件事缺一件，用户就会把模板当成稿子。
