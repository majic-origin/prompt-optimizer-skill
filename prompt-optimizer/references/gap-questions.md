# 缺口问题库

按任务类型挑问题。先归类，再决定追问还是绕过。

分类口径与 SKILL.md 一致：

| 类 | 处理 |
|---|---|
| A 可澄清 | 追问，最多两轮，每个问题带选项或默认值 |
| B 可推断 | 直接用行业默认值，产出里标"默认采用 X，如不符请告知" |
| C 素材型 | 不追问，不编造，用 `{{占位符}}` 挂起并附替换说明 |

C 类的识别标志：答案只存在于用户手上，常常不在文字里。实物外形、私有数据、原始文件、个人经历、品牌资产都属这类。

通用三问，任何类型都可能用到，都属 A 类：

1. 产出物是什么形态？选项：一段文字 / 一份文件 / 一段代码 / 一个方案对比
2. 产出物给谁用、拿到之后干什么？
3. 有没有明确不要的东西？

## 写作类

A 类：

- 体裁与篇幅。选项：公众号长文 2000 字 / 短帖 300 字 / 报告 / 小说章节
- 受众与场合。给同行看还是给外行看，公开发表还是内部沟通
- 是否已有一稿。有稿是改，没稿是写，两者流程不同

B 类：语气取正式书面，结构取总—分—结，人称跟随体裁。

C 类：

- 要写的具体事件、人物、私人体感。用户没说就挂占位符
- 用户自己的经历细节。个人素材无法从外部推断

必问的一句：用户说的"润色"到底指什么。改错别字、重写句子、重构结构是三件事，产出物差别极大。

## 代码类

A 类：

- 语言、框架、版本
- 运行环境：本地、容器、线上服务
- 现有代码是否可改，还是必须新增文件
- 验收方式：跑通测试、能启动、仅要代码片段

B 类：注释语言取中文，命名取英文，不引入新依赖。

C 类：

- 用户私有工程的结构与内部约定。看不到代码就写占位符，不假设它长什么样
- 内部接口文档、私有 SDK 的实际行为

多问一句边界：这段代码是替换现有实现，还是并列新增。答错会导致覆盖用户的既有逻辑。

## 分析类

A 类：

- 判断依据来自哪里：用户给的材料，还是需要外部检索
- 结论强度：给建议、给结论、只列可能性
- 有没有必须回答的具体问题

B 类：结构取结论先行，篇幅取千字内，不确定处显式标注。

C 类：

- 用户手里那份数据的实际内容。没拿到只能给分析框架，不下结论
- 用户所在业务的实际背景。行业黑话与内部流程无法推断

外部检索这一项必须问。需要检索却不问，等于默认允许编造来源。

## 数据类

A 类：

- 数据来源与文件位置
- 口径定义：时间范围、样本范围、单位、是否去重
- 产出形态：表格、图表、一段解读

B 类：缺失值显式标注，不做插值，单位随原数据。

C 类：

- 数据文件本身。没拿到文件只能写加工脚本，跑不出任何数字
- 业务口径里只有内部人才知道的规则

单位与口径不问清，算出来的数字看着对，实际含义已经变了。

## 设计类

A 类：

- 目标平台与尺寸
- 参考对象：有没有喜欢的例子
- 必须包含的元素：标题、署名、二维码、logo

B 类：主色跟随题材，字体取系统可用字体，留白比例偏保守。

C 类：

- 品牌资产：logo 原件、标准色值、指定字体文件
- 产品实拍图与人物照片

"好看"不是约束。要么给出参考，要么给出三条可判定的标准。

## 其他类

通用兜底三问，都属 A 类：

1. 这件事做完之后，你拿它去做什么？
2. 心里有没有一个合格例子，描述一下它长什么样？
3. 时间、成本、平台这三项里，有没有哪项是硬限制？

## 提问写法

问题句要能一个字答完。三条写法：

- 给选项：要长文还是短帖，长文按 2000 字算
- 给默认：按公众号长文处理，不对就说
- 给推断：从你说的"周报"推断受众是直属上级，对吗

避免开放问句。问"你想要什么样的风格"，用户回一句"自然一点"，缺口依然存在。问"按口语化处理还是按书面处理"，一个字就能回。

## 两轮之后

两轮问不完就到顶了。剩下的按类分流：

- 能推断的按 B 类填默认，并在产出里标注
- 素材型的按 C 类挂占位符，附"补哪一项即可使用"的替换说明
- 用户催进度时，把剩余缺口列成待确认清单，标明用了什么默认值、改动会影响哪部分产出

用户事后纠正时，只重做受影响的部分。
